Read the prerequisites

Everything is generated locally in this page. No paths are uploaded or saved. Your browser cannot verify that a folder exists or run the installer; you review and execute the copied command yourself. No credentials are requested here.

Start here: complete steps 1–7 once per development setup, then use steps 8–10 for each PBI. Run setup from the extracted package folder; run development commands from your repository root.
STEP 1

Check your Windows development tools

Use an interactive Windows desktop with Visual Studio and GitHub Copilot. Install these prerequisites before opening the setup wizard.

  • Visual Studio: a supported version with GitHub Copilot Chat, Agent mode and a working Copilot entitlement. Update Visual Studio and the Copilot components if Agent mode or custom agents are unavailable.
  • .NET: SDK 8 or later and a runtime compatible with this .NET 8 tool. Installing an SDK alone does not guarantee the required runtime is installed.
  • Git for Windows: available in the terminal, with your normal repository authentication.
  • Windows PowerShell 5.1 and WPF: required for the final desktop commit dialog. Your organization must allow the installed script to run.
  • Repository access: an existing local checkout, access to required package feeds and a C# test project with a compatible Coverlet collector.

Open PowerShell and check:

PowerShell
dotnet --list-sdks
dotnet --list-runtimes
git --version
$PSVersionTable.PSVersion

Expect an SDK version of 8 or later, an appropriate Microsoft.NETCore.App runtime, a Git version, and Windows PowerShell 5.1 or later for the dialog host. SDK 8 is the simplest matching development setup.

STEP 2

Extract the complete package

  1. Download Akzo-SDD-Agent-v3.1.1.zip.
  2. Right-click the ZIP and choose Extract All. Do not run setup from inside the compressed ZIP.
  3. Open the extracted Akzo-SDD-Agent-v3.1.1 folder.
  4. Keep Setup-AkzoSddAgent.cmd, tool/, agent/, and this guide together. The tool folder must contain Akzo.Sdd.Tool.3.1.1.nupkg.

The installer uses the packaged C# tool. You do not need to compile the engine to install it.

STEP 3

Prepare your repository

Use your existing local checkout and its root folder—the folder containing Git metadata. Example: C:\src\AN.ColorAppsAzure.BL. Record your actual solution filename and integration branch.

PowerShell
Set-Location "C:\src\AN.ColorAppsAzure.BL"
git status --short
git branch --show-current
git rev-parse --verify origin/develop

Replace origin/develop if your team uses a different integration branch. Resolve a missing ref using your team's normal fetch process. Review existing changes; the final commit dialog includes all proposed changed files and refuses pre-existing staged changes. Preserve unrelated work and handle it separately in Visual Studio.

STEP 4

Run the first-time setup wizard

  1. Double-click Setup-AkzoSddAgent.cmd in the extracted folder.
  2. The wizard checks .NET and Git, then installs the sdd tool for your Windows user.
  3. Enter or drag in the repository root path.
  4. Select Auto-detect, or choose DAB or CDMS explicitly for your C# backend.
  5. Read the installation and health-check output. Repeat for another repository only if needed.

For a scripted installation, run this from the extracted package folder:

PowerShell
.\Setup-AkzoSddAgent.cmd /silent dab "C:\src\AN.ColorAppsAzure.BL"

Use cdms for ColorDMS. The package retains UI assets, but the new automatic server-scanning workflow in this release supports .NET builds, not Angular/TypeScript scanning.

The setup wizard does not install Visual Studio, Git, missing SDKs, business-project test dependencies or Sonar server access. A warning or failed health check needs attention; it does not mean every prerequisite was prepared automatically.

The package ships the dialog as a .ps1.template; the installer creates CommitDialog.ps1 in your repository. NuGet installation does not execute this dialog.

STEP 6

Configure your solution, tests and Sonar project

Open .sdd/settings.json in the repository. Merge the relevant fields into the existing file; preserve team-specific settings. Replace the example solution, integration branch, Sonar host and project key below.

JSON
{
  "role": "DAB",
  "integrationBranch": "origin/develop",
  "buildCommand": "dotnet build YourSolution.sln",
  "testCommand": "dotnet test YourSolution.sln --no-build --logger trx --collect:\"XPlat Code Coverage\" --results-directory \"{results}\"",
  "coverageThreshold": 90,
  "localSonar": true,
  "requireServerSonar": true,
  "sonarUrl": "https://your-sonar-server.example/",
  "sonarProjectKey": "your-project-key",
  "sonarOrganization": null,
  "sonarScannerVersion": "10.4.1"
}
  • buildCommand / testCommand: use the actual solution path relative to the repository root. Keep {results}; the engine replaces it with a unique results directory.
  • Coverlet: target test projects must already reference a compatible coverlet.collector. The agent does not silently change business-project dependency files. A dotnet test runner with the XPlat collector produces the required coverage.
  • sonarUrl: the real HTTPS service URL. For SonarCloud, use your organization's correct regional service URL and set sonarOrganization.
  • sonarProjectKey: an existing project you may analyze. Its gate, quality profile, new-code definition and exclusions should match team policy.
  • Branch support: the scanner supplies the current branch. Your Sonar plan/edition must support that branch analysis; otherwise final verification blocks.
  • Network: allow your actual Sonar service, required package feeds and scanner/JRE download destinations through your organization's supported network configuration.

Local analysis is enabled by default. Final verification requires server analysis by default and installs pinned SonarScanner for .NET 10.4.1 into .sdd/tools/ when first needed. The scanner provisions a compatible JRE where supported; restricted environments may need an administrator-provided runtime/trust configuration.

STEP 7

Supply Sonar credentials securely

Provide SONAR_TOKEN through your approved secret-management process to the process environment used by the agent's terminal. The token must permit analysis submission and reading the quality gate.

For a temporary PowerShell session, enter it through a masked prompt:

PowerShell
$sonarCredential = [System.Management.Automation.PSCredential]::new('sonar', (Read-Host 'Sonar token' -AsSecureString))
$env:SONAR_TOKEN = $sonarCredential.GetNetworkCredential().Password
Remove-Variable sonarCredential

This sets the token only for that PowerShell process and its future child processes. It does not update already-running Visual Studio or separate Copilot terminals. For agent use, have your approved secret manager launch/configure Visual Studio with the required environment, or run commands from the credential-equipped terminal where supported. Restarting Visual Studio alone does not transfer a temporary token from another terminal.

Never put the token in settings.json, a script, a commit, a screenshot or chat. To check presence without showing its value:

PowerShell
if ([string]::IsNullOrWhiteSpace($env:SONAR_TOKEN)) { 'SONAR_TOKEN missing' } else { 'SONAR_TOKEN present' }

After a temporary session, remove it with Remove-Item Env:SONAR_TOKEN when no longer needed.

STEP 9

Understand verification and independent review

  1. Targeted checks: real build, executed tests, coverage and local Sonar analyzer feedback.
  2. Final checks: scanner begin → rebuilt solution → tests/current coverage → scanner end → exact submitted task's analysis ID → server quality gate.
  3. Independent review: the reviewer checks the approved requirements, actual diff and final evidence. Source changes invalidate evidence.
  4. Review seal: after a genuine passing review, the reviewer records sdd review-seal.

The engine and instructions cannot create a missing IDE API. If your Visual Studio/Copilot version cannot invoke the independent reviewer automatically, the agent reports the limitation and asks for one reviewer switch. It must not approve its own implementation as independent review.

Optional manual diagnostics from the repository root:

PowerShell
sdd verify --scope targeted
sdd verify --scope final

A failed or missing required check blocks delivery. Missing credentials, unsupported branch analysis or failed feeds must be corrected; do not disable checks to force a pass.

STEP 10

Review the final popup and commit locally

After final checks and sealed independent review pass, the agent runs sdd finish. It refreshes final verification, validates the review, generates PR-description text for later manual use and launches a standalone Windows desktop dialog.

  • Confirm the repository and branch.
  • Read every proposed changed file. All listed files will be committed; unrelated changes must be handled before this step.
  • Review the check summary and edit the commit message if needed.
  • Select Commit Locally to authorize staging and committing, or Cancel to stop. Closing the window also cancels.

Cancel/close stages nothing. Existing staged work, changed source, a changed file list or stale review blocks the automated commit. Git hooks stay enabled. A hook failure can leave files staged; inspect them manually. If a hook changes committed content, the tool reports that a commit was created and needs renewed verification without resetting it.

To reopen the popup while all evidence is still current:

PowerShell
sdd commit-dialog

This is a WPF window launched from the terminal, not an embedded Visual Studio dialog. It needs an interactive Windows desktop and permission to run the supplied script. When execution is blocked, use your organization's signing/approval process; do not bypass policy.

After a successful commit, the agent reports the commit hash. You handle push, PR creation and merge manually in Visual Studio. No PR or merge is created by this flow.

The local gate now explicitly requests CS0169, CS8618, S1144 and S3242. A real disposable C# build reproduced all four supplied findings and the gate rejected each one. This does not establish the current state of your Azure DevOps PR.

FindingImplementation action
